# Workbench host operations runbook

This runbook covers first-time host bootstrap, safe updates to an existing
daemon, base-image releases, rollback, reboot verification, and host removal.
The control-plane deployment procedure is in the repository README.

Adding a host requires this procedure plus one D1 hosts row. It must not require
dashboard or daemon source changes.

The destructive capacity and isolation gate for a staging host is
[MULTITENANT_TESTING.md](./MULTITENANT_TESTING.md).

## 1. Environment classes

### Current development host

The current host is a small Debian VPS with a file-backed, unencrypted ZFS
pool. It is suitable for integration testing and one free environment after
reserve. It is not a production storage or availability design.

Never describe data on that host as encrypted, backed up, or recoverable after
host loss.

### Production host requirements

A production host requires:

- Debian 12 or 13 and root SSH access;
- enough physical RAM and disk for advertised capacity plus host reserve;
- a real ZFS pool with native encryption;
- a documented key-unlock procedure for unattended and attended reboot;
- tested monitoring, certificate renewal, restore, and incident procedures;
- a DNS hostname and publicly trusted TLS certificate for the daemon;
- restricted daemon ingress or mTLS/private connectivity when that control is
  implemented; and
- explicit acceptance of the current no-backup limitation, or a backup design
  completed before taking user data.

The bootstrap script can create a loop-backed ZFS pool for development, but it
does not turn that pool into production storage.

## 2. Prerequisites

On the operator workstation:

- Node.js 22, npm, rsync, SSH, and a clean repository checkout;
- authenticated Wrangler access to the intended Cloudflare account;
- the configured D1 database and KV namespace; and
- the Worker RPC public key generated by apps/worker/scripts/genkeys.ts.

On the host:

- Debian 12/13 with working DNS and outbound package access;
- root SSH;
- Incus kernel support; and
- ports 80, when using Certbot standalone, and 8443 available.

Generate control-plane/host keys once:

    cd apps/worker
    npx tsx scripts/genkeys.ts

Store WORKER_RPC_PRIVATE_KEY only as a Worker secret. Supply only the printed
public key to hosts.

## 3. First-time host bootstrap

### 3.1 Prepare storage

For production, create and document an encrypted pool before bootstrap. The
exact vdev layout is operator-specific; a minimal example is:

    zpool create \
      -O encryption=on \
      -O keyformat=passphrase \
      -O keylocation=prompt \
      tank /dev/DEVICE

Test the load-key and mount procedure after a reboot before accepting users.

For a disposable development host, bootstrap can create a file-backed pool:

    ZFS_LOOP_GB=40

This stores an unencrypted zpool image on the host filesystem. It is
development-only.

Provide at least 1 GiB of host swap per expected tenant slot before bootstrap.
Each free container is capped at 1 GiB of swap by Incus; the aggregate host
capacity prevents tenants from competing for an undersized swap device. For a
four-slot host without an existing swap partition, one option is a dedicated
4 GiB swap file on the host root filesystem:

    fallocate -l 4G /swapfile
    chmod 600 /swapfile
    mkswap /swapfile
    swapon /swapfile
    echo '/swapfile none swap sw 0 0' >> /etc/fstab

Do not place the swap file inside the tenant storage pool.

When applying this policy to an existing host, drain it first and notify users:
the policy script updates existing free containers live from 2 GiB RAM/no swap
to 1.5 GiB RAM/1 GiB swap, enabling swap before lowering RAM to avoid a
transient tighter ceiling. Active workloads can still see reclaim latency.
Apply migration `0011_free_tier_memory.sql` while the host remains drained so
D1 reservations match the Incus limits before the host returns to active
placement.

### 3.2 Copy and bootstrap

From the repository root:

    rsync -a \
      --exclude node_modules \
      --exclude .git \
      --exclude .wrangler \
      --exclude '.dev.vars*' \
      --exclude '.env*' \
      ./ root@HOST:/opt/workbench/

Then:

    ssh root@HOST \
      'HOST_ID=HOST_ID WORKER_RPC_PUBLIC_KEY=BASE64_PUBLIC_KEY \
       bash /opt/workbench/infra/bootstrap.sh'

For the development loop pool, add ZFS_LOOP_GB=40 to that environment.

Cloud kernels may not include ZFS. If bootstrap reports a missing module,
install the appropriate cloud kernel, headers, and zfs-dkms, reboot, confirm
the module loads, and rerun bootstrap.

Bootstrap:

- installs Incus, Node.js 22, nftables, and supporting packages;
- creates or attaches a quota-capable Incus storage pool and refuses a silent
  dir-pool fallback;
- creates a restricted `workbench` tenant project with aggregate capacity,
  anti-spoofing, east-west isolation, and bandwidth limits;
- installs the outbound-port-25 and new-connection-rate rules;
- installs the repository dependencies and daemon systemd unit;
- creates the host X25519 credential keypair;
- creates an initial daemon configuration; and
- prints a D1 host-registration command.

The generated private key remains in /etc/workbench/daemon.json, mode 0600.
Back it up only through the host-secret backup process. Never copy it into D1
or the repository.

Before activating the host, run the read-only policy audit:

    ssh root@HOST \
      'cd /opt/workbench && bash infra/audit-multitenant.sh'

The bootstrap registers a conservative 3:1 vCPU ceiling, all detected physical
RAM except a fixed 2 GiB host reserve, and 70% of pool capacity. The actual
1 vCPU/1.5 GiB RAM/1 GiB swap tenant count is the minimum of CPU, RAM, and 10 GiB
root-plus-home disk slots; bootstrap also requires enough host swap for every
resulting slot.

### 3.3 Build and verify the base image

    ssh root@HOST \
      'bash /opt/workbench/infra/build-image.sh'

The image must contain all base tools and all four agents. Current builds
resolve the latest npm versions at build time; record the observed versions in
the release notes. Verify with an ephemeral container:

    ssh root@HOST '
      set -eu
      incus delete -f cs-image-smoke 2>/dev/null || true
      trap "incus delete -f cs-image-smoke >/dev/null 2>&1 || true" EXIT
      incus launch workbench-base cs-image-smoke
      incus exec cs-image-smoke -- sh -lc "
        id dev
        for tool in ssh git gh python3 uv node rg fd bat jq sqlite3 cmake \
          rsync nano zip tree less man; do
          command -v \$tool
        done
        for package in libssl-dev libsqlite3-dev manpages; do
          dpkg-query -s "\$package" | grep -Fx 'Status: install ok installed'
        done
        for agent in pi claude codex opencode; do
          command -v \$agent
        done
        npm list -g --depth=0
      "
      incus delete -f cs-image-smoke
      trap - EXIT
    '

If verification fails, do not register the host active.

### 3.4 Configure trusted TLS

A deployed Worker cannot call a raw HTTPS IP endpoint and does not trust the
bootstrap self-signed certificate. Give the daemon a hostname. sslip.io can be
used for disposable development, but it is a third-party wildcard service with
shared certificate-rate limits.

Obtain a certificate:

    certbot certonly --standalone -d DAEMON_HOSTNAME

Set these fields in /etc/workbench/daemon.json:

    "tlsCertPath": "/etc/letsencrypt/live/DAEMON_HOSTNAME/fullchain.pem",
    "tlsKeyPath": "/etc/letsencrypt/live/DAEMON_HOSTNAME/privkey.pem"

Install a renewal hook:

    install -d /etc/letsencrypt/renewal-hooks/deploy
    printf '%s\n' '#!/bin/sh' \
      'systemctl restart workbench-daemon' \
      > /etc/letsencrypt/renewal-hooks/deploy/workbench-daemon.sh
    chmod 0755 /etc/letsencrypt/renewal-hooks/deploy/workbench-daemon.sh
    systemctl restart workbench-daemon

Verify the timer and certificate:

    systemctl is-enabled certbot.timer
    certbot renew --dry-run
    openssl s_client -connect DAEMON_HOSTNAME:8443 \
      -servername DAEMON_HOSTNAME </dev/null 2>/dev/null |
      openssl x509 -noout -subject -issuer -dates

TLS provides server authentication and transport encryption. The current
Worker does not pin daemon_cert_fp and does not present an mTLS client
certificate. Every daemon request is additionally Ed25519-signed, and
credential payloads are sealed to the host X25519 key. mTLS/private ingress is
planned hardening, not a current control.

The simple Certbot hook above restarts the daemon and therefore clears its
in-memory jobs and nonce cache. It is acceptable on the current development
host only. A production deployment should terminate TLS in a proxy that reloads
certificates without restarting the daemon, or coordinate certificate restarts
with the drain and active-job checks in section 4.

### 3.5 Register the host

Use the SQL printed by bootstrap, but set:

- ssh_hostname to the hostname users should put in SSH commands;
- daemon_endpoint to https://DAEMON_HOSTNAME:8443;
- capacity to conservative usable values after host overhead;
- ram_reserve_mb to retained headroom; and
- status to active only after every verification step passes.

Run the command from apps/worker so Wrangler finds the correct configuration:

    cd apps/worker
    npx wrangler d1 execute workbench --remote --command "INSERT ..."

Confirm:

    npx wrangler d1 execute workbench --remote --command \
      "SELECT id, ssh_hostname, daemon_endpoint, vcpu_capacity,
              vcpu_allocated, ram_total_mb, ram_allocated_mb, ram_reserve_mb,
              disk_total_gb, disk_allocated_gb, last_seen_at,
              consecutive_failures, status
       FROM hosts ORDER BY id"

Complete a real signup, provision, fingerprint check, and SSH login before
calling the host ready.

## 4. Safe release to an existing daemon

Do not rerun bootstrap as an update mechanism. It mixes package, firewall,
storage, key, and registration work. Use this release procedure instead.

### 4.1 Local release gate

From a clean checkout:

    npm ci
    npm run typecheck
    npm test
    git status --short

Understand whether the release changes:

- only the Worker;
- daemon source or dependencies;
- packages/contract wire behavior;
- the systemd unit or host configuration; or
- infra/build-image.sh and image contents.

A Worker-only change does not require a daemon restart. An image-only change
does not require restarting the daemon or existing containers.

### 4.2 Drain placement

Set the target host to draining before copying code. This prevents new
placements and FIFO waitlist admission on that host while existing containers
continue running:

    cd apps/worker
    npx wrangler d1 execute workbench --remote --command \
      "UPDATE hosts SET status = 'draining' WHERE id = 'HOST_ID'"

Confirm it:

    npx wrangler d1 execute workbench --remote --command \
      "SELECT id, status FROM hosts WHERE id = 'HOST_ID'"

### 4.3 Check for active jobs

Restarting the daemon loses its in-memory job registry and nonce cache. Existing
running containers are unaffected, but queued or running operations are not.

Query D1:

    npx wrangler d1 execute workbench --remote --command \
      "SELECT j.id, j.op, j.status, j.updated_at,
              c.id AS container_id, c.status AS container_status
       FROM jobs j
       JOIN containers c ON c.id = j.container_id
       WHERE c.host_id = 'HOST_ID'
         AND j.status IN ('queued', 'running')
       ORDER BY j.created_at"

The result must be empty. Also inspect the host:

    ssh root@HOST '
      set -eu
      systemctl is-active workbench-daemon
      incus --project workbench list
      incus storage info default
      df -h / /opt
    '

If a job is active, wait for it to finish and query again. Do not restart,
cancel, or mark it complete merely to continue a release.

### 4.4 Back up the current release

Configuration and host X25519 keys live under /etc/workbench and are not
replaced by this release. Back up source/lockfiles and the unit for rollback:

    ssh root@HOST '
      set -eu
      umask 077
      stamp=$(date -u +%Y%m%dT%H%M%SZ)
      tar --exclude=workbench/node_modules \
        --exclude="workbench/.dev.vars*" \
        --exclude="workbench/.env*" \
        -C /opt -czf "/root/workbench-$stamp.tgz" workbench
      cp /etc/systemd/system/workbench-daemon.service \
        "/root/workbench-daemon-$stamp.service"
      echo "release backup stamp: $stamp"
    '

Record the printed stamp in the release notes.

### 4.5 Copy, install, and restart

The operator workstation must have rsync. Copy without --delete so
node_modules and host-local material are not removed:

    rsync -a \
      --exclude node_modules \
      --exclude .git \
      --exclude .wrangler \
      --exclude '.dev.vars*' \
      --exclude '.env*' \
      ./ root@HOST:/opt/workbench/

Install deterministic production dependencies, update the unit, and restart:

    ssh root@HOST '
      set -eu
      cd /opt/workbench
      npm ci --omit=dev --workspaces --include-workspace-root
      install -m 0644 \
        apps/daemon/systemd/workbench-daemon.service \
        /etc/systemd/system/workbench-daemon.service
      systemctl daemon-reload
      systemctl restart workbench-daemon
      systemctl is-active --quiet workbench-daemon
      journalctl -u workbench-daemon -n 30 --no-pager
    '

Do not rotate /etc/workbench/daemon.json or the X25519 key during an ordinary
release. Rotation requires updating the host public key in D1 in coordination
with the daemon.

### 4.6 Verify before undraining

On the host:

    ssh root@HOST '
      set -eu
      systemctl is-enabled workbench-daemon
      systemctl is-active workbench-daemon
      systemctl show workbench-daemon \
        -p MainPID -p ExecMainStartTimestamp --no-pager
      journalctl -u workbench-daemon --since "-5 minutes" --no-pager
      incus --project workbench list
    '

From outside the host, an unsigned health request must reach the daemon and be
rejected with 401:

    test "$(curl -sS -o /dev/null -w '%{http_code}' \
      https://DAEMON_HOSTNAME:8443/health)" = 401

This proves reachability and fail-closed request authentication, not a complete
signed Worker-to-daemon path. For a daemon or shared-contract release, perform
a controlled lifecycle job from the Worker and confirm D1 reaches succeeded.
If the base image also changed, perform provision-to-SSH.

Only then return the host to service:

    cd apps/worker
    npx wrangler d1 execute workbench --remote --command \
      "UPDATE hosts SET status = 'active' WHERE id = 'HOST_ID'"

Confirm no new Worker/daemon errors during the next reconciler interval.

## 5. Daemon rollback

Leave the host draining if verification fails. Use the backup stamp captured
before release:

    ssh root@HOST '
      set -eu
      stamp=BACKUP_STAMP
      systemctl stop workbench-daemon
      mv /opt/workbench \
        "/opt/workbench.failed-$(date -u +%Y%m%dT%H%M%SZ)"
      tar -C /opt -xzf "/root/workbench-$stamp.tgz"
      cd /opt/workbench
      npm ci --omit=dev --workspaces --include-workspace-root
      cp "/root/workbench-daemon-$stamp.service" \
        /etc/systemd/system/workbench-daemon.service
      systemctl daemon-reload
      systemctl start workbench-daemon
      systemctl is-active --quiet workbench-daemon
      journalctl -u workbench-daemon -n 30 --no-pager
    '

Repeat the verification in section 4.6. Return the host to active only after
the rollback is healthy. Preserve the failed tree and logs until the incident
is understood.

Rollback does not recover an in-flight job that was lost during restart. The
Worker should surface that job as failed/error and offer the appropriate retry.

## 6. Base-image release

### Rebuild triggers

Rebuild workbench-base when any of these change:

- infra/build-image.sh;
- Debian base release or security state;
- Node, uv, shell, SSH, or development-tool versions;
- an intended coding-agent version or image refresh;
- SSH hardening or dev-user setup; or
- the scheduled security refresh cadence.

Do not rebuild it for Worker-only or daemon-only logic changes.

### Safe rebuild

The build script force-deletes any Incus instance named cs-image-build. Reserve
that name exclusively for image builds.

Drain the host first so provisioning cannot start during the resource-intensive
build. Record the current image fingerprint:

    ssh root@HOST \
      'incus image info workbench-base | sed -n "1,12p"'

Then:

    ssh root@HOST \
      'bash /opt/workbench/infra/build-image.sh'

Run the ephemeral image verification from section 3.3. Existing containers are
not changed by repointing the alias. New provision/rebuild jobs use the new
image.

Keep the prior fingerprint until the new image passes provision-to-SSH. To
restore the alias:

    ssh root@HOST '
      set -eu
      incus image alias delete workbench-base
      incus image alias create workbench-base PRIOR_FULL_FINGERPRINT
    '

Return the host to active after validation.

## 7. Coordinated Worker, daemon, and schema changes

The safest order for a backward-compatible shared change is:

1. apply an expand-only D1 migration;
2. drain and deploy a daemon that accepts both old and new requests;
3. deploy the Worker that emits the new request;
4. verify a real job and one reconciler interval;
5. undrain the host; and
6. remove old fields only in a later release.

Never deploy mutually incompatible Worker and daemon versions and rely on a
fast restart to hide the interval. Worker rollback does not reverse a D1
migration, and daemon rollback does not reverse Worker code.

## 8. Reboot behavior and verification

Containers use `boot.autostart=last-state`: running tenants return after a host
restart, while deliberately stopped tenants remain stopped. The daemon is
enabled under systemd. After a reboot:

    ssh root@HOST '
      set -eu
      systemctl is-active workbench-daemon
      systemctl is-active nftables
      incus --project workbench list
      nft list table inet workbench
      zpool status
      zfs get encryption,keyformat,keylocation
    '

For encrypted production storage, load its key through the documented
procedure before declaring recovery complete. Verify an existing SSH
connection, then allow one Cron interval for D1/Incus state reconciliation.

## 9. Certificate and log checks

Useful commands:

    systemctl status workbench-daemon --no-pager
    journalctl -u workbench-daemon -n 100 --no-pager
    journalctl -u workbench-daemon --since today --no-pager
    certbot certificates
    systemctl list-timers certbot.timer

The public endpoint will receive unsigned probes. They should appear as
rpc_rejected and return 401. Repeated probes do not prove compromise, but a
large increase warrants rate-limiting and ingress review. Logs must never
contain credential payloads or values.

## 10. Decommissioning or a dead host

Drain a planned decommission first:

    cd apps/worker
    npx wrangler d1 execute workbench --remote --command \
      "UPDATE hosts SET status = 'draining' WHERE id = 'HOST_ID'"

Because the current release has no migration or backup restore, do not destroy
a host with user environments unless every user has removed/exported their
data and the corresponding D1 rows are reconciled.

For an unrecoverable host:

    npx wrangler d1 execute workbench --remote --command \
      "UPDATE hosts SET status = 'dead' WHERE id = 'HOST_ID'"

Treat all local environments as lost. Preserve incident evidence, prevent new
placement, reconcile capacity/state deliberately, and communicate the known
no-backup outcome.

## 11. Security invariants

- /etc/workbench/daemon.json and its TLS private key are mode 0600.
- The X25519 private key never leaves the host; only its public half is in D1.
- The Worker RPC private key never leaves Cloudflare Secrets.
- Every daemon request requires a valid Ed25519 signature, timestamp, and
  nonce. Nonces are in memory and reset on daemon restart.
- Credential payloads are sealed to the destination host and are never stored
  in D1 jobs or daemon logs.
- Outbound forwarded TCP port 25 is dropped.
- New outbound IPv4 and IPv6 connections are capped per container source
  address.
- The daemon operates in the restricted `workbench` project; tenant NICs
  enforce anti-spoofing, east-west isolation, and bandwidth limits.
- Each tenant has CPU, hard memory, process, root-disk, and home-disk ceilings.
- Password and root SSH login are disabled in the image.
- Development file-backed storage is unencrypted and must never be presented
  as production-safe storage.

## 12. Supply-chain gap

Coding-agent packages and missing-binary fallback installers are currently
unpinned npm installs. Until exact versions and an SBOM are produced
automatically:

- retain complete image-build logs;
- record npm list -g --depth=0 in the release evidence;
- test all four binaries before repointing the alias; and
- treat a later fallback install as potentially different from the baked image.
